# Развёртывание

## Development

Команды из корневого README собирают все три части. `npm run dev` запускает собранный API, Vite-панель и готовую веб-сборку Flutter на loopback. Для изменения API перезапустите `npm run build` или отдельно используйте `backend: npm run start:dev`.

Для Android Emulator запустите `flutter run` в `mobile`: адрес хоста по умолчанию `http://10.0.2.2:3001`. Debug-манифест разрешает локальный HTTP. Для физического устройства передайте HTTPS-адрес API через `--dart-define=API_BASE_URL=...`; сервер должен быть доступен устройству. Release Android не разрешает произвольный cleartext HTTP.

На Windows с кириллицей в пути отдельные версии Flutter analysis server могут ошибаться на инициализации. В этом случае используйте свободную букву диска:

```powershell
subst T: "C:\путь\к\проекту"
cd T:\mobile
flutter analyze
flutter test
```

Если T: занята, выберите свободную букву. После работы из другого каталога выполните `subst T: /D` только для созданного вами подключения.

Корневые команды setup/build/check делают такое подключение автоматически при кириллице в пути и снимают его после завершения. Не запускайте несколько Flutter-сборок или проверок этого проекта одновременно: генератор локализаций и build cache общие.

## Production API

1. Выделите PostgreSQL, приватные S3-совместимые bucket'ы либо постоянный файловый том, HTTPS-домен и отдельную БД staging. Перед миграцией сделайте backup.
2. Установите зависимости `npm ci`, соберите `npm run build`, запускайте `node dist/main.js` из каталога `backend`. `drizzle` должен находиться рядом с `dist`: миграции применяются на старте.
3. Передайте переменные окружения через менеджер секретов. Для production обязательны `NODE_ENV=production`, `DATABASE_URL`, HTTPS `PUBLIC_BASE_URL`, три разных секрета длиной не менее 32 символов, `ADMIN_REQUIRE_MFA=true`, `OTP_DELIVERY=webhook`, `OTP_WEBHOOK_URL`, `OTP_WEBHOOK_TOKEN`. Настройте явный список `CORS_ORIGINS` для приложения и панели.
4. `STORAGE_DRIVER=s3` требует `S3_BUCKET_PUBLIC` и `S3_BUCKET_PROTECTED`, endpoint/region и credentials согласно провайдеру. **Оба bucket'а должны быть закрыты для публичного чтения.** Название `PUBLIC` обозначает обработанные варианты; выдача всё равно идёт через API с проверкой состояния объявления. Без S3 и постоянного диска (бесплатный Render) используйте `STORAGE_DRIVER=db`: фото хранятся в PostgreSQL.
   `PHOTO_REVIEW`: при `after` (по умолчанию) объявление с фото, которое AI не проверил, публикуется сразу, а модератор проверяет его в «Обращениях»; при `before` оно скрыто до одобрения модератором.
5. Создайте первого администратора служебной командой, подключите приложение аутентификации при первом входе. Запретите доступ посторонних к CLI и БД.
6. Ограничьте API доверенным reverse proxy. Не размещайте его напрямую в интернете без корректной настройки IP и rate limits. Приложение ожидает один proxy hop (`trust proxy=1`).

Сгенерируйте каждый секрет отдельно:

```powershell
node -e "console.log(require('node:crypto').randomBytes(48).toString('base64'))"
```

Админ-панель: `npm ci && npm run build` в `admin`; раздавайте `dist` через HTTPS. Проксируйте `/v1` к API или задайте `VITE_API_BASE_URL` перед сборкой. Flutter Web собирается с HTTPS `API_BASE_URL`; раздавайте `mobile/build/web`. Сервер должен возвращать `index.html` для маршрутов приложения. Базовый пример инфраструктуры находится в `infra`.

Пример Compose запускается командой `docker compose -f infra/compose.yaml up --build -d` после подготовки backend/.env и переменной POSTGRES_PASSWORD. Для пароля PostgreSQL в этом примере используйте hex/буквенно-цифровую строку, чтобы она была корректна внутри DATABASE_URL. HTTPS завершается вашим внешним reverse proxy; открытые порты примера привязаны к loopback. Docker-конфигурация подготовлена, но в текущей среде Docker отсутствует и контейнеры не проверялись.

## Доставка SMS/email

Backend отправляет POST на настроенный relay с `Authorization: Bearer <OTP_WEBHOOK_TOKEN>`, JSON:

```json
{"channel":"phone","destination":"+996700000001","code":"123456","locale":"ky","expiresInSeconds":300}
```

Второй канал — `email`. Ваш relay преобразует запрос в API выбранного SMS/email-провайдера, проверяет bearer token и возвращает 2xx только после принятия сообщения. Не пишите коды и адресатов в обычные журналы. Таймаут — 10 секунд, redirects запрещены. Ошибка relay возвращает клиенту 503. Для выбора и проверки реального провайдера нужны ваши реквизиты; код не делает фиктивную доставку.

`PUSH_DRIVER=console` — единственный реализованный системный push transport. Уведомления в БД и в приложении работают. Не задавайте `fcm`, пока не реализован и не проверен адаптер и регистрация токенов на мобильных устройствах.

## AI

По умолчанию `AI_PROVIDER=disabled`; публикация и поиск работают, фото идут на ручную проверку. Для Anthropic укажите `AI_PROVIDER=anthropic`, `ANTHROPIC_API_KEY`, `AI_MODEL` с моделью, доступной вашему аккаунту. Модель по умолчанию не выдумывается. Перед отправкой реальных фото оцените и оформите правила обработки у внешнего провайдера. Интеграцию необходимо проверить на staging с реальными разрешёнными образцами.

## Android / iOS

Android: установите Android SDK/JDK, проверьте `flutter doctor`, создайте собственный upload keystore. Скопируйте `mobile/android/key.properties.example` в `key.properties`, заполните значения. Файл и keystore исключены из Git. Без него release-сборка намеренно останавливается; debug-подпись не выдаётся за release.

```powershell
flutter build appbundle --release --dart-define=API_BASE_URL=https://api.example.kg
```

iOS: требуется macOS с Xcode, CocoaPods, Apple Developer Team и signing/provisioning. Проверьте Bundle ID `kg.tabyldy.tabyldy`, настройте team, privacy usage descriptions и соберите `flutter build ipa --release --dart-define=API_BASE_URL=...`. На Windows iOS-сборка не выполнялась.

## Эксплуатация и восстановление

Используйте один API instance на первом пилоте: локальные rate limits и текущие задачи планировщика не являются распределёнными. `REDIS_URL` зарезервирован и пока не подключает распределённые очереди.

Проверяйте `/v1/health` и поле `status`, а не только HTTP-код. Собирайте stderr/stdout в централизованный журнал с ограничением доступа и сроком хранения. Настройте алерты на degraded DB, рост 5xx и переполнение диска. Подключение APM/crash reporting и внешних алертов — отдельная задача эксплуатации.

Ежедневно делайте `pg_dump` БД и версионируйте приватное хранилище. Зашифрованные копии держите отдельно от сервера. В staging восстановите `pg_restore` и объекты; проверьте вход, объявление, приватное вложение и завершение возврата. Зафиксируйте фактические RPO/RTO. Такой recovery drill пока не выполнялся.

Не откатывайте код поверх несовместимой схемы. Перед изменением миграций сохраняйте БД; при инциденте остановите запись, восстановите согласованные БД/медиа в отдельной среде и переключите трафик после проверки.
